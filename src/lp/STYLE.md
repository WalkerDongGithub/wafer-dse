# lp2 编码规范

## 0. 最高原则：代码服务于论文

论文是根本目的，代码是实现工具。

- 代码与论文冲突 → 改代码
- 论文产生变化 → 代码做对应调整
- 论文没提到的（产品级校验、异常处理、边界检查） → 可以删
- 论文需要的（运行结果、日志、实验数据） → 必须做好

**这不是一个产品，这是一篇论文的配套代码。**

---

## 1. 一个文件只解释一件事

文件目录结构反映概念之间的层级关系。

- 每个文件开头三行讲清楚：这个概念是什么、在整个框架里的角色、怎么用
- 读者应能在**不理解其他模块**的情况下，读懂当前模块的逻辑
- 如果一个文件里同时出现了两个概念（比如 engine 里既做 store 又做 solver），就拆

---

## 2. 抽象做 ABC，实现可替换

如果一个概念的实现工具与这个概念本身无关，抽 ABC。

- `Model`：其本质是"定义约束"→ 不关心用什么求解器 → ABC
- `CvxEngine`：求解器不一定永远是 cvxpy → 留接口
- `ResultStore`：存储不一定永远是目录文件 → 留 `_Backend`

**具体的实现我们不关心，关心的是接口。**

---

## 3. 统一的编码结构

### 文件结构

1. 顶层 docstring —— 核心概念、存在意义、用法、读者指南
2. import
3. 数据类（如果有）
4. ABC（如果有）
5. 默认实现
6. 内部辅助

### 注释风格

**顶层 docstring 回答三个问题：**

1. 这个文件解决什么问题？（存在意义）
2. 怎么用？（一行示例）
3. 读者应该读哪里、可以跳过哪里？（读者指南）

**分段注释解释"这部分解决什么"：**

```python
# ========================================================================
# 这部分是什么？
#   变量声明——ctx.vector/scalar/var 三个方法。
#   读者：需要知道怎么声明变量 → 读这里。内部实现 → 可以跳过。
# ========================================================================
```

不是"这个函数做了什么"——是"这部分代码在整体中扮演什么角色"。

**告诉读者什么时候可以跳过：**
```python
    # -- 内部（读代码时可跳过）----------------------------------------------
```
这个标注很关键——减少读者的阅读负担。

### 校验代码

大多数用不到 → 删掉。除非绕不过去或出了 bug。
出了 bug 的校验，在头部写清"这个 bug 是什么、为什么必须防"。
---

## 4. 日志与结果保留

运行结果 = 实验数据 → 论文的原材料，必须妥善保管。

- `ResultStore`：每次求解落盘，meta.json 记录完整性
- `Runner`：缓存透明，同参数不解两次
- 日志：帮助调试 + 作为实验记录的一部分

日志和存储同样要遵守 ABC 原则——`ResultStore` 有 `_Backend`，未来可以换存储介质。
