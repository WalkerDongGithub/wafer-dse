## 开篇：逻辑 PHY 管什么？

规范 p97 开门见山列出了 7 项职能。但我不打算逐条念——我用一句话概括：

**逻辑 PHY 是物理层里跑数字逻辑的那部分。它不碰电压和电流——那是 AFE 的活。它管的是：数据怎么分配到每根 Lane、链路怎么训练、坏 Lane 怎么绕、时钟什么时候可以关。**

AFE 是身体，逻辑 PHY 是大脑。

## 第一讲：数据怎么在物理线上跑

### 1.1 一个基础事实：每个节拍，每根 Lane 传 1 Byte 的 1 bit

规范 4.1.1 节（p97-99）定义了一个简单但影响深远的规定：

> Each Byte is transmitted on a separate Lane. Byte 0 (B0) is transmitted on Lane 0, Byte 1 is transmitted on Lane 1 and so on.

你有一个 256B 的 Flit。物理层有 64 根 Lane（x64 Advanced Package）。传输方式是：

```
时刻 0（第 0 个 UI）：
  Lane 0 传 Byte 0 的 bit 0, Lane 1 传 Byte 1 的 bit 0, ..., Lane 63 传 Byte 63 的 bit 0

时刻 1（第 1 个 UI）：
  Lane 0 传 Byte 0 的 bit 1, Lane 1 传 Byte 1 的 bit 1, ...

...

时刻 7（第 7 个 UI）：
  Lane 0 传 Byte 0 的 bit 7, ..., Lane 63 传 Byte 63 的 bit 7

时刻 8（第 8 个 UI）：
  Lane 0 传 Byte 64 的 bit 0, ...（下一轮 64 字节）
```

**也就是说：64 根 Lane 并行传输，每 8 个 UI（加上开销）传完 64 字节，256 字节的 Flit 需要 4 轮 × 8 UI = 约 32 UI。**

这个映射方式意味着：**物理层的宽度和 Flit 的字节布局是绑定的。x64 接口一次传 64 Byte，x32 一次传 32 Byte，x16 一次传 16 Byte。** 如果你做了宽度退化（比如 Lane Repair 后从 x64 降到 x32），适配器必须知道——因为 RDI 的有效宽度变了。

### 1.2 Valid 信号：定义"什么时候该听"

所有 Lane 一直在传输——即使没有 Flit 要发，线上也有电压。接收端怎么知道"现在是有效数据"还是"噪音/空闲"？

规范 4.1.2 节定义了一个 **Valid 信号**——这是一个独立的物理线（每 Module 一根），它高电平的时候，数据 Lane 上的内容才是有效的。

> The transmitted data is framed by the valid signal.

**Valid 是数据 Lane 的"闸门"。** 它有两个作用：
1. **帧定界**：接收端只看 Valid 为高时的数据
2. **时钟门控**：Valid 为低时，接收端可以关掉数据路径的时钟

对体系结构来说：**Valid 是"链路利用率"的物理指标。** 如果链路空闲，Valid 一直低，PHY 自动进入 Clock Gating 省电——不需要适配器介入。如果链路满载，Valid 一直高，功耗就拉到峰值。

### 1.3 Clock Gating：空闲时的省电机制

规范 4.1.3 节（p100-101）定义了时钟门控。这个机制的动机非常简单但在体系结构层面很重要：

> 链路空闲时，Mainband 可以不传任何东西。Valid 拉低。接收端检测到 Valid 持续为低 → 自动关掉数据路径的时钟 → 省电。恢复时拉高 Valid → 接收端重新打开时钟 → 开始接收。

**整个过程不需要 Sideband 消息，不需要适配器参与，不需要序列号重置。** 这就是 Table 5-2 里 "Idle Exit/Entry Latency = 0.5-1 ns" 的来源——它只是时钟重新稳定的时间，不是链路重训练。

**这对体系结构意味着什么？** 你可以把"时钟门控 idle"想象成**零代价的微睡眠**。数据 burst 之间即使只隔了几十个 Flit 时间，PHY 也可以自动关钟省电，几乎不影响延迟。不需要 OS 参与，不需要适配器协商。

### 1.4 Sideband 传输的两个模式

Sideband（800MHz）是独立于 Mainband 的低速通道。规范 4.1.5 节定义了两种传输模式：

**常规模式**：每个 Sideband 消息封装成一个 64-bit 串行包，在 Sideband 的 Data 线上逐 bit 传输。简单可靠，但慢。

**PMO（Performant Mode Operation）**：如果两端都支持，Sideband 可以跑得更快——允许背靠背（back-to-back）连续发送多个 64-bit 包，不需要等待确认。

> Sideband Performant Mode Operation means that Back-to-Back Sideband transmissions are permitted.

**PMO 的价值**：常规模式每发一个包都要等确认 → 延迟大。PMO 允许连续发包 → 吞吐量高。链路训练期间（MBTRAIN）涉及大量 Sideband 消息交换——PMO 可以显著缩短训练时间。

**对你的意义**：训练时间是 PMO 是否使能的一个函数。如果你的系统对"上电到可用"的延迟敏感，你应该使能 PMO。

## 第二讲：链路训练 — 整个逻辑 PHY 的核心

这是第四章最长、最重要的部分（4.5 节，p122-169，约 48 页）。

### 2.1 训练要解决的根本问题

刚上电时，两端 PHY 互相之间知道什么？**什么都不知道。**

- 不知道对面有几根 Lane（x64？x32？x16？）
- 不知道每根 Lane 的信号延迟是多少（走线长度未知）
- 不知道接收端的最佳采样电压（Vref）和采样时刻
- 不知道 Lane 有没有物理损坏
- 不知道对面 Lane 的物理顺序和逻辑顺序是否一致（走线可能交叉）

**链路训练就是通过 Sideband 协调，加上在 Mainband 上发已知测试模式，让两端逐一回答上述问题。**

### 2.2 MBTRAIN：训练的主状态机

规范把训练分解为 MBTRAIN 的 13 个子状态（p155-165）。我不逐一解释每个——那对你是噪声。我把它们按**做什么**分组：

#### 组 1：模拟前端校准（4 个子状态）

```
MBTRAIN.VALVREF      — 校准 Valid Lane 的接收参考电压
MBTRAIN.DATAVREF     — 校准 Data Lane 的接收参考电压
MBTRAIN.SPEEDIDLE    — 在最低速率下发空闲模式，让 PLL 和时钟树稳定
MBTRAIN.TXSELFCAL    — 发送器自校准（输出阻抗调整）
MBTRAIN.RXCLKCAL     — 接收端时钟校准（调整 PI 相位，找到时钟边沿）
```

**这些是"模拟电路调参"。对体系结构的意义：这些步骤的耗时取决于 PHY 实现，但它们只在初始训练时发生一次（或 Retrain 时）。不影响稳态性能。**

#### 组 2：Valid 和时钟训练（2 个子状态）

```
MBTRAIN.VALTRAINCENTER — 找 Valid Lane 上信号的中心采样点
MBTRAIN.VALTRAINVREF   — 校准 Valid Lane 的 Vref
```

**Valid Lane 必须先训练好——因为 Valid 是数据 Lane 的"闸门"，闸门不准，后面的数据训练都白费。**

#### 组 3：数据训练（3 个子状态）

```
MBTRAIN.DATATRAINCENTER1 — 第一轮：找到每根 Lane 数据眼图的中心采样点
MBTRAIN.DATATRAINVREF    — 优化每根 Lane 的 Vref
MBTRAIN.DATATRAINCENTER2 — 第二轮：基于最优 Vref 重新找中心采样点
```

**为什么数据训练要做两轮？** 因为采样时刻和 Vref 是互相依赖的。第一轮在默认 Vref 下找最佳采样时刻，然后基于那个采样时刻找最优 Vref，然后基于新的 Vref 再精调采样时刻。**这是一个迭代收敛过程，和通信系统里的均衡器训练逻辑一样。**

#### 组 4：偏移校正

```
MBTRAIN.RXDESKEW — 消除 Lane 间偏移
```

64 根 Lane 的物理走线长度不可能完全相同（几微米的差异在 32 GT/s 下就会产生可测的偏移）。DESKEW 测量每根 Lane 的相对延迟，在接收端补偿——让所有 Lane 的 bit 在逻辑上对齐。

**从体系结构角度：DESKEW 决定了 x64 接口的"有效并行宽度"。如果某根 Lane 的偏移超过补偿范围，它就不能和其余 63 根同步——必须被禁用。**

#### 组 5：速率协商和修复

```
MBTRAIN.LINKSPEED — 速率协商：从低到高尝试，找到最高可用速率
MBTRAIN.REPAIR    — Lane 修复：检测坏 Lane，用冗余 Lane 替换
```

LINKSPEED 的过程是：从最低速率（4 GT/s）开始，一级一级往上尝试（4→8→12→...），每级做一次快速训练，如果能通过就继续往上。**找到的最高可用速率就是最终运行速率。**

REPAIR 在第三讲详细展开。

### 2.3 训练完成后：LINKINIT → ACTIVE

训练完成后进入 LINKINIT——一个很短的过渡状态，做最后的初始化和 Sideband 同步。然后进入 ACTIVE——RDI 从 Reset 变为 Active，适配器可以开始 Stage 3 的参数交换。

### 2.4 对体系结构的关键数字

规范没有给出每个训练子状态的具体耗时（实现差异太大），但整个训练分成了 13 步，每一步都需要 Sideband 握手（至少一轮请求/响应）。按 Sideband 常规模式（每轮 ~160 ns），13 步 × 多轮握手 ≈ **几微秒到几十微秒**的级别，加上模拟电路的校准时间（PLL 锁定、Vref 扫描），总训练时间可能在**几十微秒到几毫秒**。

**Retrain 走同样的流程（可能跳过部分已达到要求的校准步骤），所以 Retrain 的耗时和初始训练是同一量级——不是"几纳秒就完事"。**

## 第三讲：故障处理 —— Lane 坏了怎么办

### 3.1 Lane Reversal：物理走线的灵活性问题

规范 4.2 节（p102-104）定义了一个看起来很奇怪的功能：Lane 反转。

**问题**：两个 Die 对接时，Die 0 的 Lane 0 必须连接到 Die 1 的 Lane 0。如果封装走线导致了物理交叉呢？比如 Die 0 的 Lane 0 连到了 Die 1 的 Lane 5。

在传统的板级设计中，这会导致 PCB 必须重新布线。在 UCIe 里，PHY 可以自动检测并纠正：**Lane Reversal 机制让接收端在训练期间发现物理 Lane 顺序和逻辑 Lane 顺序不一致，然后自动重新映射。**

**对体系结构的意义**：这给了封装设计更大的自由度。封装工程师不必为了保证"Lane 0 对 Lane 0"而增加走线层数或绕线。**性能和封装成本之间增加了一个可以调整的维度。**

### 3.2 Lane Repair：物理冗余

规范 4.3 节（p105-113）是本章除了训练之外最重要的部分。

**问题**：封装制造中，bump 可能坏（开路、短路）。在 x64 的 64 根 bump 中，即使良率是 99.9%，也有 6% 的概率至少坏一个 bump。如果坏了整个 Module 就不能用，良率损失太大了。

**解决方案**：Advanced Package 额外提供 4 根冗余数据 Lane（TXDATARD[3:0] 和 RXDATARD[3:0]），以及冗余的 Clock、Valid、Sideband 信号。

**单 Lane 修复**：64 根 Lane 中任意 1 根坏了 → 用冗余 Lane 替换。所有 Lane 逻辑右移一位，"跳过"坏的那根。

**双 Lane 修复**：任意 2 根坏了 → 用 2 根冗余 Lane 替换。同样的逻辑移位。

**修复决策流程**：训练期间（MBTRAIN.REPAIR），PHY 对每根 Lane 发测试模式，检查接收质量。质量不合格的 Lane 被标记为坏。然后在 REPAIR 状态里执行重新映射。

> 规范 p107-111 用伪代码详细定义了 x64 和 x32 的修复算法。核心逻辑是：检查每根 Lane → 标记坏的 → 按"跳过坏的、用冗余替"的规则重新分配逻辑 Lane 到物理 Lane。

**对体系结构的关键含义**：

1. **Lane Repair 改变了有效带宽吗？** 不。如果修复成功，仍然有 64 根有效 Lane（只是映射到了不同的物理 bump 上）。带宽不变。

2. **修复可以减少有效宽度吗？** 会，如果坏 Lane 超过冗余数量。x64 有 4 根冗余 → 最多修 4 根？实际上规范允许 1-2 Lane 修复。超过 → 宽度退化（x64 → x32）。

3. **修复信息需要通知适配器吗？** 不。修复是 PHY 内部的事——逻辑 Lane 到物理 bump 的映射由逻辑 PHY 处理，RDI 接口上看到的仍然是 64 Byte 的标准宽度。适配器完全不知道底下的"哪根物理 bump 被替换了"。

4. **修复的可靠性代价**：修复后的链路 BER 和原来一样——你只是换了一根 bump，电气特性类似。但如果冗余 bump 也用完了 → 只能降宽度。**冗余 bump 是一种保险——用额外的物理 bump 换取了制造良率的提升。**

## 第四讲：多模块扩展

### 4.1 问题：一条 x64 不够怎么办？

规范 4.7 节（p170-177）定义了多模块链路。你可以把 2 个或 4 个 Module 聚合成一条更宽的链路：

```
1 × x64 = 64 Lanes = 256 GB/s @ 32 GT/s
2 × x64 = 128 Lanes = 512 GB/s
4 × x64 = 256 Lanes = 1024 GB/s（1 TB/s！）
```

多个 Module 由一个公用的 MMPL（Multi-Module PHY Logic）协调。MMPL 负责把适配器送来的数据分配到各个 Module，并在接收端重新组装。

### 4.2 同步问题：所有 Module 必须对齐

多模块的不同 Module 之间，时钟相位可能不同。MMPL 需要在训练期间做**跨模块对齐**——确保所有 Module 的数据在逻辑上同步。

规范 p171-174 花了大量篇幅定义多模块初始化的 Sideband 消息流。核心问题：
- 每个 Module 有自己的 Sideband → 对端怎么知道"这个 Sideband 对应哪个 Module"？
- 每个 Module 独立训练 → 怎么保证训练同时完成？
- 如果一个 Module 训练失败 → 其他 Module 怎么办？

### 4.3 宽度退化 vs 速度退化 vs 模块禁用

多模块场景下，训练失败的三种后果（规范 p175-176 给了详细示例）：

| 结果 | 触发 | 后果 |
|------|------|------|
| **宽度退化（Width Degrade）** | 某 Module 的部分 Lane 坏 | 该 Module 宽度降级（x64→x32） |
| **速度退化（Speed Degrade）** | 某 Module 达不到目标速率 | 所有 Module 统一降速（32→24→16...） |
| **模块禁用（Module Disable）** | 某 Module 完全不可用 | 该 Module 被排除，其余继续 |

**一个重要的规则**：多模块下，**所有 Module 必须跑相同速率。** 所以速度退化是"全局"的——一个 Module 掉速，全体一起降。

宽度退化可以逐模块——Module 0 跑 x32、Module 1 跑 x64 是可以的。

### 4.4 对体系结构的含义

多模块本质上是用**更多的物理 bump 换更高的带宽**。代价是：

1. **芯片边沿面积**：每个 Module 约 388μm 宽、~1000μm 深。4 个 Module ≈ 1.5mm 边沿长度——在先进工艺的芯片边沿上这是不小的面积。

2. **功耗线性增加**：4 个 Module = 4 倍的 PHY 功耗。虽然 UCIe PHY 本身很省电（0.3 pJ/bit），但 1 TB/s 仍需 ~300 mW 的 PHY 功耗——这并不是可以忽略的。

3. **故障概率增加**：更多 bump = 更高概率至少一个 bump 坏。但这正是 Lane Repair 存在的原因。

## 全章总结：逻辑 PHY 就是物理层的"操作系统"

如果说 AFE 是物理层的"裸机"（电压、电流、时钟），逻辑 PHY 就是物理层的"操作系统"——它管理 Lane 资源、调度训练流程、处理故障、协调多模块。

**对体系结构者，你需要的不是一个电路实现方案，而是一个行为模型**：

- 上电到 ACTIVE 需要多少时间？（几十微秒到几毫秒）
- Retrain 中断多久？（同上量级）
- Lane Repair 能修到什么程度？（1-2 Lane，修不了就降宽度）
- 多模块怎么扩展？（线性带宽增长、线性能耗增长、故障影响局部化）
- 空闲时省电有多快？（Clock Gating ≤ 1 ns）

这些就是第四章给你的答案。
